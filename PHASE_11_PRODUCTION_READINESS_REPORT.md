## 2. MANDATORY LAUNCH GATE EVALUATION: PAYMENT GATEWAY

The prompt mandated an independent, rigorous technical and regulatory evaluation of the repository-integrated payment gateway:
**Repository:** https://github.com/youpi-pg/YouPI-PG.git (YouPI PG V2)

### 2.1. Technical Architecture & Reverse Engineering Analysis
YouPI PG is an experimental, self-hosted utility designed to automate peer-to-peer (P2P) Unified Payments Interface (UPI) collections. It operates by:
1. Running an Android companion APK on a physical Android smartphone.
2. Intercepting bank SMS text messages or Android notification listener events.
3. Parsing notification strings using regular expressions to extract customer amounts and bank Unique Transaction References (UTRs).
4. Relaying parsed transactions to an Express/Node.js server that fires webhooks to merchants.

### 2.2. Failure Modes & Production Risks Identified
1. **Regulatory Non-Compliance (RBI Guidelines):**
   - Under Reserve Bank of India (RBI) master directions for Payment Aggregators and Payment Gateways (PA/PG), entities accepting digital customer funds must hold a valid PA/PG license, maintain segregated escrow accounts, and adhere to strict PCI-DSS and cyber-resilience guidelines.
   - YouPI PG holds no regulatory license and operates outside authorized merchant rails. Processing commercial customer payments through it constitutes a regulatory breach.
2. **Single-Slot FIFO Deadlock (Amount Collision):**
   - Because UPI QR codes generated by P2P handles do not support dynamic merchant reference tags (unless on commercial merchant VPA rails), YouPI PG relies on matching the exact rupee amount.
   - If two patrons attempt to check out simultaneously for identical totals (e.g., ₹25,200), the gateway cannot deterministically match which customer paid which UTR without queuing them sequentially or adding artificial paisa deltas. Under concurrent luxury drops, this causes order processing deadlocks.
3. **No Programmatic Refund Infrastructure:**
   - YouPI PG provides zero refund endpoints. Returns, order cancellations, and chargebacks cannot be executed via API and require manual UPI bank transfers outside the software.
4. **Fragile Bank Scraper Dependencies:**
   - Any bank SMS template modification or Android battery-saver throttling halts webhook notifications, causing paid orders to remain indefinitely in `pending` payment status.

### 2.3. Architectural Isolation in Vélure Atelier
The Vélure Atelier engineering team correctly recognized these limitations during Phase 07 and established a clean adapter pattern:
- `PaymentProvider` interface in `src/services/payment/types.ts`.
- Experimental gateway isolated in `src/services/payment/youpiProvider.ts`.
- Safe test sandbox isolated in `src/services/payment/mockProvider.ts`.
- **Production Safeguard:** In `src/services/payment/mockProvider.ts` and `youpiProvider.ts`, if `process.env.NODE_ENV === 'production'` and `process.env.ALLOW_TEST_PAYMENTS !== 'true'`, any attempt to initialize a test payment session is strictly rejected.

### 2.4. Production Gateway Verdict
- **Classification:** **(3) Experimental or insufficiently verified integration** (YouPI PG) alongside **(2) Test-only integration** (Mock Provider).
- **Production Policy:** Real commercial funds must **NOT** be processed through YouPI PG. Commercial launch requires registering a certified PA/PG adapter (e.g., Razorpay).

## 4. DOMAIN VERIFICATION SUMMARY

### 4.1. Catalog, Discovery & Variant Availability
- Dynamic server and static generation for collections (`/collections/[slug]`) and products (`/products/[slug]`).
- Variant availability accurately reflects inventory: products with stock > 0 display as available, variants with 0 stock are disabled in the size picker with "Sold Out" badges.
- Unpublished or draft garments are strictly filtered from storefront listings.

### 4.2. Cart, Wishlist & Stock Reservation
- Hybrid persistence: Guest carts stored in local storage and reconciled securely upon authentication; authenticated carts persist in Supabase `carts` and `cart_items`.
- Quantity capping prevents adding more than currently available inventory (`quantity_on_hand - quantity_reserved`).

### 4.3. Checkout, Pricing Recalculation & Order Placement
- **Zero Browser Trust:** Browser-submitted totals, shipping fees, taxes, and coupon discounts are discarded. The server recalculates everything from the trusted product catalog.
- **Taxation & Shipping:** Correctly applies 12% GST on discounted garment subtotals. Complies with free shipping threshold (>= ₹5,000 standard complimentary).
- **Atomic Stock Reservation:** Reserving stock atomically increments `inventory_reservations` prior to order creation.
- **Idempotent Checkout:** Idempotency keys prevent duplicate order creation on rapid double-clicks.

### 4.4. Order Lifecycle & Fulfillment
- Independent, decoupled state machines for fulfillment (`pending` -> `confirmed` -> `processing` -> `tailoring` -> `dispatched` -> `delivered`) and payment (`pending` -> `paid` -> `refunded`).
- **Cancellation:** Customers can cancel eligible orders (`pending` / `confirmed`); stock reservations are immediately released.
- **Returns:** 14-day return window enforced from `deliveredAt`. Approved returns restock physical inventory with audit logging.

### 4.5. Security, IDOR Defense & Admin Studio
- Customer orders enforce session validation: an attacker cannot view or tamper with another customer's order.
- Admin studio routes (`/admin/*`) and privileged server actions enforce `assertAdminUser()`.
- Phase 11 hardened `src/lib/adminAuth.ts` to strictly deactivate heuristic whitelist patterns in production.
- Sensitive environment secrets are never exposed in store settings API payloads.

### 4.6. Shipping, Logistics & Notifications
- Postal pincodes validated against Indian 6-digit postal format.
- Tracking URLs sanitized against XSS and pseudo-protocols.
- Resend REST email dispatcher prevents duplicate customer emails using deterministic idempotency keys (`${eventType}_${orderNumber}_${modifier}`).
- Payment confirmation emails are strictly gated on verified `paid` state.
